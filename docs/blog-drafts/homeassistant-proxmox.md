My Home Assistant installation works, but its Raspberry Pi hardware is unreliable. Migrating the application is an opportunity to establish a VM platform with configuration and recovery instructions in the homelab repository.

## The host choice is about dependencies

Both candidate servers, epsilon and culex, have the same dual Xeon CPUs and 64 GB RAM. epsilon carries the Kubernetes API address, the shared PostgreSQL datastore, and GPU-pinned workloads. Its Debian installation supports a package-based Proxmox conversion after a rehearsed Debian 13 upgrade. Accepting planned downtime provides an opportunity to prove physical-node recovery and discover maintenance friction before an emergency.

The layout is Proxmox on epsilon with a general-purpose Kubernetes server guest, a GPU worker guest, and Home Assistant OS. Distinct guest identities permit staging while pods remain on physical k3s. The P1000 moves only when GPU consumers stop; two nodes cannot use the same passthrough card simultaneously. The Kubernetes API endpoint also needs an explicit transition before physical k3s retirement.

## Native manifests are a useful first interface

Proxmox stores guest hardware in a colon-separated configuration file. Keeping templates in Git gives production guests and a minimal network probe explicit CPU, memory, disk, firmware, MAC, passthrough, and startup settings. Documented `qm` commands allocate the actual disks, whose generated volume IDs are then recorded in the manifests.

That is a small foundation rather than an automatic configuration reconciler. The important boundary is clear: Git describes hardware and operational intent; off-host backups preserve the appliance's state. A configuration file by itself does not allocate a disk or restore Home Assistant.

A small standard-library Python renderer prints staging `qm` commands directly from those templates. It keeps CPU/RAM/MAC/disk allocations in one manifest and separates staging from final auto-start and device handoff. Its tests use the actual guest manifests and round-trip shell quoting, so preparing commands does not require a running hypervisor. Host network/storage fragments and a stable API endpoint design can also be reviewed remotely while physical imaging waits.

## Preserve network identity, transfer ownership

The internal Home Assistant DNS record already points to `192.168.1.134`. Preserving that address lets cutover update the OPNsense DHCP reservation from the Pi's MAC to the VM's persistent MAC. The guest uses a LAN bridge, so discovery protocols can reach the same network without NAT.

DNS resolving does not prove the application is usable. The checks include browser login, live updates, and the existing remote-access path from outside the LAN. IPv6 addresses and a Pi-hosted VPN agent need separate attention because an IPv4 reservation and an application backup do not migrate them.

## The Zigbee dongle is part of the appliance

The radio must physically move from the powered-off Pi to the server. Proxmox USB passthrough selects a unique vendor/product ID or a physical port; Home Assistant selects the resulting guest serial path by its persistent by-id name. These identifiers operate at different layers.

The same coordinator and its restored application state should retain the network's pairings. Seeing the adapter in `lsusb` on the host is only the first check. The guest must see it, the owning Zigbee integration must open it, and real devices must report and respond. A light's physical response, a battery sensor event, and an automation provide much better evidence than a green VM status.

Moving the radio can also change RF coverage. An extension cable keeps it away from the server chassis and USB interference; a distant-room device test checks whether the rack location is practical.

## Accept downtime, keep rollback simple

Physical-node rehearsal starts with an offline image captured from a verified SystemRescue USB to an independent host. A changing live ext4 root is not a consistent disk-image source. Even before an OS upgrade, boot recovery requires usable console/media access and sufficient transfer/hash time; the full raw disk transfer is hundreds of gigabytes. Booting a private clone proves more than package dependency resolution alone.

The full499.6GB image matched the unmounted source SHA256. Culex's XFS reflink support made a separate writable working inode without another full transfer, while preserving the private master. The NIC-less libvirt VM then exposed a recovery dependency that hashing cannot test: firmware boot entries live in the motherboard's variable store, not the raw disk. Registering the existing Debian shim in the VM's OVMF variables enabled boot; a cleared replacement motherboard may need the same step.

After clone-only service/network-mount/console preparation, Debian booted normally with no failed units. The captured PostgreSQL17.5 image opened the local datastore, read its kine rows, passed a temporary SQL roundtrip and a clean restart. GPU drivers and an obsolete suspend/resume UUID needed clone hardware adjustments. None of that proves a physical disk overwrite, GPU operation under an upgraded kernel or remote-PVC recovery; it establishes a useful, bounded recovery test before package changes. The [boot rehearsal record](../plans/epsilon-debian-upgrade.md#nic-less-image-boot-and-datastore-verification-passed-october-8) keeps those claims explicit.

Package access needs its own boundary because the disk also carries production client credentials. A dedicated bridge without a default route or DNS lets the clone reach only a package-host-allowlisted Squid proxy. Bridge-scoped firewall rules block direct host and forwarded LAN access; the proxy rejects private/tailnet destinations and unlisted hosts. Real tests prove package HTTP/verified HTTPS succeeds while production API, NAS, host SSH and cloud control-plane access fails. Existing host Kubernetes/Podman firewall tables remain in place.

Fresh Bookworm indexes exposed a dependency problem that the earlier dry-run did not: security sources admitted non-free firmware without the corresponding non-free NVIDIA drivers. Matching source components resolved the proprietary driver/firmware version mismatch before package installation. The prepared shut-off disk, VM firmware and domain definition are retained together, so package experiments can return to a known bootable starting point. The [package-access record](../plans/epsilon-debian-upgrade.md#restricted-package-access-and-prepared-baseline) captures the source decision and bounded recovery claims.

The clone completed Bookworm12.15 and then Debian13.7 with reviewed minimal/full transactions. It booted the6.12.111 kernel, compiled proprietary NVIDIA modules, authenticated a fresh local SSH session and ran the captured PostgreSQL17.5 datastore under Docker29.9 without pulling another image. A reviewed libvirt conffile prompt preserved its local UID/GID settings. Trixie's automatic VM SSH socket generator and newly enabled NFS helper needed isolation-specific handling; the accepted reboot has zero failed units and no error-level boot logs. Prepared/Bookworm/Trixie disk-and-firmware checkpoints remain retained. Actual physical NIC/PERC/GPU operation, k3s networking and application workflows remain separate acceptance work; [the result](../plans/epsilon-debian-upgrade.md#debian-13-clone-rehearsal-accepted-october-8) records that boundary.

On physical epsilon the Bookworm patch came first, followed by a separately notified Trixie window. Fresh SQL/configuration copies were verified off-host before normal node drain, full remote-volume release and a logged PostgreSQL shutdown checkpoint. Trixie's package changes completed, but the running OpenSSH9.2 listener could no longer create sessions after its executable was replaced by10.0: `-R not supported here`. The existing SSH/tmux session continued. Configuration validation and a targeted listener restart restored fresh access, allowing physical kernel/headers/DKMS/initramfs/PERC/NIC/EFI checks before reboot.

The server then booted Debian13.7/kernel6.12.111 with its original LAN identity, NAS mounts, k3s/datastore and GPU. The P1000's proprietary550.163 driver and Jellyfin/Tdarr encoder/persistence checks pass; the database image stays17.5 and the retained CI listener reconnects under Docker29.9. Final privileged APT/fstab/storage checks passed after correcting the public source file's permissions. This is bounded operational proof, not every user's workflow. Historical storage flags and application follow-ups remain recorded; a pre-existing Obsidian Dropbox sync issue stays offline for manual recovery. ## Test the VM platform before importing the appliance

The LANbridge keeps epsilon's `.69` management address and physical MAC, with `eno1` as an unnumbered bridge port. ISC reservations are not exclusions: the management address had to leave the dynamic pool before static assignment. OPNsense's ISC Save handler can reconfigure DHCP immediately, so a Save-only staging step is not inherently harmless. Jack reported applying the reviewed ranges; actual host renewal and the probe's `.221` lease provide client evidence, while router configuration/parser backups were not supplied.

A separate ext4 filesystem backs `vm-local`. Its mountpoint guard was tested by unmounting before guest allocation: the storage went inactive instead of writing into the root filesystem. A controlled host reboot then proved bridge, resolver, local storage and host NFS persistence. Host DNS uses OPNsense directly with Tailscale DNS acceptance disabled, avoiding a NAS boot dependency on tailnet split DNS.

Debian preseed installs a small probe with a disk-size guard, key-only SSH and a guest agent. A private derived ISO carries the password hash and public key; it stays outside Git. The guest obtains its reserved lease and passes bounded LAN/DNS/verified HTTPS, MTU, actual mDNS discovery and guest NFS write/fsync/read tests. Same-host iperf measures the virtual path, and a forced Tailscale subnet connection from a Mac still on the LAN does not prove physically off-site access. The [probe matrix](../plans/proxmox-network-probe.md#observed-probe-results) preserves these limits and remaining diagnostics.

The first stop-mode VM backup produced an 882 MB archive on the NAS. Its full hash was checked before restoring it under unused VMID198. The NIC was removed before first boot because changing a VMID does not replace the copied hostname, DHCP identity or SSH keys. EFI boot, the expected OS, installation marker and guest agent passed with only loopback networking; clean shutdown leaves the restore VM and archive retained for review. Notification delivery failed because the default mail target had no recipient and host mail was local-only. Jack deferred delivery setup as a required follow-up before production backup schedules.

Home Assistant staging comes before Kubernetes guest migration while Jellyfin users are active. The Pi inventory identifies HAOS18.3, 10.6 GiB used and a dual-interface HubZ coordinator owned by ZHA. Its configured Zigbee port is interface01; passing through the physical USB device must preserve that choice. A fresh full backup includes the recorder, Zigbee database and all installed apps, with captured SQLite integrity checks and matching private off-host copies. The empty x86 VM passes onboarding, DNS/verified HTTPS, guest reboot and clean shutdown on a temporary lease. Its automatic first boot installs current Core, while the supported full restore selects the backup's Core version.

The failing Pi then rebooted unexpectedly with hundreds of undervoltage warnings. Replacing its cable did not restore reliable access, so Jack accepted the already verified full backup for cutover and retained the powered-off source media. The x86 restore brought back dashboards and apps, but my radio attachment happened too early: empty HA onboarding can automatically discover USB and form a Zigbee network before account creation. The restored ZHA database detected the changed channel/PAN/key and blocked startup. Its native repair restored the original saved network to the same coordinator; private key comparison and existing-device physical control verified recovery without re-pairing. The procedure now restores HA before attaching the production radio, with Core stopped during attachment.

The restored Tailscale app needed local reauthentication, then retained the same name/IP and passed phone-on-mobile-data login. Guest reboot preserves USB/network/control; native HA and stop-mode VM archives are protected off-host. Restoring the latter into a NIC/USB-less guest verifies boot and captured recorder/Zigbee integrity while the production appliance stays live. The final `.134` exclusion waited for a maintenance window. Private router configuration/lease copies and current/intermediate/final parser tests preceded the UI changes; the live generated configuration then matched the candidate, and the VM acquired its reservation without a reboot.

An address change also affects application-owned bindings. The Tailscale app's forwarding rule used the local address captured at startup, and Core's discovery socket still used the temporary IP. Supervisor's watchdog rebuilt forwarding by restarting the unhealthy Tailscale app; a scoped Core restart refreshed mDNS. Normal DNS/HTTP/SSH, actual mDNS service discovery, physical Zigbee control and phone-on-mobile-data login verified the preserved `.134` service identity. Scheduled backup notifications and broader device/host-boot checks remain explicit acceptance work.

Running two restored copies concurrently risks duplicate automations and cloud/MQTT clients even when only one has a radio. Restore tests therefore keep copied network and USB identities isolated.

Rollback reverses ownership: stop the VM and disable its auto-start, move the radio back, restore the Pi's reservation/access settings, and boot its intact media. Keep coordinator firmware and pairings stable throughout the move.

Recovery is a separate proof. The plan uses daily native HA backups, weekly stop-mode VM backups, and an isolated restore exercise. VM archives do not include the radio's NVRAM or Kubernetes's external datastore/PVs. Those dependencies need their own copies and instructions.

## Stage Kubernetes guests with distinct identities

The Kubernetes guests are `eps-base` (server) and `eps-gpu` (agent), each with a separate static LAN address, MAC and OS disk. An unattended installer has a single-disk capacity guard, key-only SSH, a standard password-protected sudo account, no swap, a guest agent and the NFS/iSCSI prerequisites. The private media contains the console password hash and public SSH key, but no production cluster tokens. k3s joins later at the actual existing cluster version with a registration-time NoSchedule staging taint. Broadly tolerating DaemonSets still need inspection; a taint is not proof that the node runs no pods. Physical GPU ownership, workload selectors and the stable API transition are separate acceptance stages.

Both guests joined the existing external-PostgreSQL cluster at `v1.32.6+k3s1`, retaining its CA and credentials. The server's direct API passed certificate-verified, authenticated reads. Forty real network checks exercised guest/physical pod paths, service DNS and existing endpoints before and after guest restarts. Unique manual-NFS test directories passed write/fsync/read/checksum and clean unmount. Only node-exporter tolerates the staging taint persistently. Stop-mode NAS backups resume both guests normally, while independent private configuration and fresh SQL copies preserve the external datastore dependency. Those captures are not boot-restore proof for the two guest archives. [Executed checks](../../agentic-investigations/2026-10-10-k3s-guests.md) retain that distinction.

The [CSI exercise](../../agentic-investigations/2026-10-10-k3s-guest-csi.md) tests the full Kubernetes storage path with one NFS and one iSCSI claim per VM. Temporary node agents retain the installed driver configuration and tolerate only the staging taint on the exact VM nodes. Four rootless pods write and fsync random data, then replacement pods verify its checksum. Each volume subsequently mounts on the opposite VM after complete unmount, detach and iSCSI-session release; the ext4 LUN never has concurrent writers. All twelve write/persistence/reattachment cases pass. Retiring temporary agents leaves the staging boundary intact; protected off-host evidence records the results. Jack subsequently approves deleting the four claims/data, verified through controller completion and read-only NAS absence queries. Tests establish the storage path, not production database recovery or concurrent-NFS stress coverage.

The first real-app migration is wedding-media, a read-only NFS consumer that can roll from culex to eps-base while its serving pod remains available. A specific staging-taint toleration admits only that pilot. Reviewed GitOps changes and actual media-range checks precede further moves; general applications will share eps-base and culex rather than all accumulating on one node. GPU consumers and the stable API retain their separate handoff stages. [Pilot plan](../plans/k3s-workload-migration.md).
